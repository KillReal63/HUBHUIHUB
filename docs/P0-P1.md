# Серверные данные и покупки

Реализовано локально; публикация и проверка на пользовательском устройстве не выполнены.

## Хранение

Питание и тренировки используют общий вход и отдельные записи `module_state`. Сервер проверяет версии, а браузер показывает сохранение только после ответа. При конфликте возвращается 409; операция не перезаписывает более свежие данные. Обновление — при возвращении и каждые 30 секунд вне редактирования. Офлайн-очередь не реализована.

`module_operations` защищает от повторной обработки запроса. Неопределённый результат отправки сохраняется в sessionStorage до подтверждения; повтор использует тот же идентификатор. `module_imports` исключает повторный импорт одной локальной копии. Исходный localStorage не удаляется. Если одноимённые идентификаторы имеют разные значения, импорт прекращается, а не выбирает произвольно одну версию.

Старые правила «Предлагать покупку» при переносе не включают реальные задачи автоматически: пользователь настраивает автопокупку явно. Старые списания становятся историческими порциями; при отмене такой порции возвращённое количество создаёт отдельную партию без известного срока годности.

## Автопокупки

У продукта есть минимум, целевой запас, режим «по остатку» или «по прогнозу», горизонт прогноза, время и часовой пояс. Начальный режим — выключено. Для режима по остатку задача появляется при количестве не выше минимума; прогноз дополнительно использует оценку расхода из размера покупки и числа дней. Истечение срока исключает партию из доступного остатка. Физическое количество от течения времени не списывается.

`food_links` содержит не более одной текущей связи на продукт. Создание задачи, изменение запаса и регистрация операции выполняются одной транзакцией. Фоновый пересчёт вызывается серверным циклом уведомлений; ошибка расчёта питания не останавливает уведомления лекарств и обычных дел.

- Пополнение выше порога закрывает покупку; частичное пополнение ниже порога уточняет количество в прежней задаче.
- Выполнение задачи само по себе не меняет запас. Выполнение или удаление подавляет новое создание в этом цикле нехватки.
- Отмена выполнения возобновляет ту же связанную задачу. Для удалённой покупки есть явное возобновление в правиле.
- После достаточного пополнения и нового снижения начинается новый цикл.
- Ручной перенос и заголовок дела сохраняются; изменяется только служебная строка количества в заметке.
- Связанная покупка остаётся разовой; обычное повторение на неё включить нельзя.
- При паузе текущая покупка закрывается; включение правила снова проверяет остаток.
- Если время сегодня уже прошло, напоминание назначается на завтра. Задача сразу доступна в периоде «Дела вообще».
- Изменение количества не меняет время уведомления и не повторяет уже отправленное уведомление. Реальная доставка зависит от устройства и не подтверждена локальными тестами.

## Партии и история

Каждое пополнение сохраняет собственное количество, дату и срок. Съеденная порция списывается сначала из непросроченных партий с ближайшим сроком; удаление порции возвращает количество в те же партии. Можно списать остаток отдельной партии. История различает покупку, расход, возврат и списание. Меню распределяет доступные партии с учётом срока на дату блюда.

## Экспорт и восстановление

В настройках хаба доступны JSON-экспорт и проверка файла. Восстановление заменяет данные всех четырёх модулей и связи покупок, повышает текущие версии и требует отдельного подтверждения после предпросмотра. Повтор того же запроса не применяет восстановление второй раз. В файл не входят учётные данные, сессии и подписки.

Перед заменой скачивается текущая копия. Сервер также сохраняет пять последних точек в `restore_points`. Эти точки — дополнительная защита для администратора, отдельного интерфейса выбора серверной точки пока нет. Внешний сервер отложен: см. [план резервирования](plans/external-backups.md).

## Сброс записей

Сброс питания и тренировок в настройках подтверждается сервером и действует на всех устройствах. Питание использует команду `reset`, очищает также партии и историю, закрывает связанные покупки и удаляет связи. Другие дела сохраняются. Локальные исходники импорта остаются в браузере; повтор ранее импортированной копии не возвращает сброшенные записи. Конфликт версии и ошибка сохранения не показываются как успешный сброс.

## API и ограничения

- `GET/POST /api/food`, `GET/POST /api/gym`: состояние, версия и операции; POST требует Origin и общую сессию.
- `GET /api/data/export`: согласованный снимок пользовательских записей.
- `POST /api/data/restore`: действия preview/restore, проверка содержимого и версий.
- Максимальный запрос API — 10 MB; интерфейс принимает файл восстановления до 9 MB. Nginx настроен на 10 MB.
- Сохраняется прежний лимит в 300 дел. Если нет места для обязательной автопокупки, операция питания отклоняется целиком с сообщением; очисти ненужные дела и повтори.
- Данные ограничены по количеству записей и размеру полей. Большие архивы требуют отдельного административного процесса, а не обхода валидации.

## Проверки и локальный просмотр

```text
python -m unittest discover -s backend -p "test_*.py"
python test-persistence.py
python test-interface.py
python preview-local.py
```

`preview-local.py` запускает весь интерфейс и API на loopback с временной пустой базой и тестовой сессией. Push отключён; данные удаляются после завершения процесса. Этот просмотр нельзя публиковать. Старые статические просмотры питания и тренировок не предоставляют новый серверный API; для функциональной проверки используй полный локальный просмотр.

## Подготовка публикации

Перед отдельным запросом на публикацию сравнить целевые файлы с сервером, сделать резервные копии кода и согласованный снимок базы. Обновлять вместе backend (`server.py`, `tasks.py`, `push_system.py`, `wellness.py`, `data_portability.py`), новые общие файлы `dist/hub/sync.*`, `dist/hub/data.js`, интерфейсы питания и тренировок, хаб и конфигурацию Nginx. Новые таблицы создаются при инициализации, старые данные и подписки не очищаются.

Исторические частичные скрипты `publish-hub.sh` и `publish-tasks.sh` не являются способом публикации этого изменения. Проверить Nginx, перезапуск API, доступ после входа, импорт из браузера и настоящий push на устройстве. При откате файлов не подменять всю рабочую базу старой копией.

## Результаты локальной проверки

32 серверных теста: в том числе конфликт двух подключений к SQLite, повтор запроса, импорт старого питания, возврат в партии, пауза/возобновление покупки, атомарность при ошибках, проверка восстановления и согласованная резервная копия. Девять существующих JavaScript-проверок прошли.

Браузерный сценарий с настоящим локальным API проверяет два устройства, отклонение устаревшего изменения, потерю ответа после записи и безопасный повтор, импорт программы, редактирование/каталог/выполнение упражнений, экспорт и восстановление. Отдельный сценарий проверяет существующие темы и интерфейсы на мобильной ширине. Проверки не обращаются к рабочей базе и не подтверждают доставку push на телефон.
