# Внешний сервер резервных копий

Статус: отложено по решению пользователя. Пользователь сообщит, какой сервер использовать и когда подключать. Никакие адреса, подключения и расписания для внешнего резервирования сейчас не настроены.

## Что уже доступно

- Ручная выгрузка пользовательских записей всех пяти модулей из настроек хаба.
- Проверка структуры файла и сравнение количества записей перед восстановлением.
- Проверка версий перед заменой: изменения после предпросмотра не перезаписываются.
- Перед восстановлением браузер скачивает текущую копию; сервер сохраняет последние пять точек восстановления в той же базе.
- Существующее резервирование SQLite охватывает новые серверные таблицы. Проверка копирования и чтения новой базы включена в автоматические тесты.

Копия в той же базе или на том же сервере не заменяет независимое хранение. JSON-выгрузка содержит пользовательские данные; пароли, сессии и push-ключи в неё не входят.

## После выбора сервера

1. Уточнить способ доступа и доступное место, периодичность, срок хранения и канал сообщения об ошибках. Секреты хранить вне Git.
2. Выделить отдельный каталог и учётные данные с доступом только к резервным копиям; определить шифрование и хранение ключа восстановления.
3. Делать согласованный снимок через SQLite backup API, проверять целостность и контрольную сумму. Переносить готовый снимок, а не копировать активный файл базы.
4. Разделить пользовательский экспорт и полное аварийное восстановление сервиса: для последнего отдельно сохранить конфигурацию и секреты с ограниченным доступом.
5. Настроить отправку, ротацию, повтор временно неудачной передачи и уведомление об отсутствии свежей копии.
6. Восстановить копию в изолированной среде, проверить все модули, связи покупок, версии и отсутствие реальной рассылки уведомлений.

Критерий готовности: копия переживает недоступность основного сервера, подтверждено восстановление в отдельную среду и понятен порядок действий при сбое.
